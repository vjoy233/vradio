# 多源电台的默认源选择与手动选源调研

> 调研日期：2026-10-13（feature/r2-batch 分支）
> 调研方法：代码走读（player.js 播放链 + app.js 装配链 + server.js 曲讯旁路）+ radio.txt 全量统计 + xmcdn/蜻蜓源网络实测（curl，国内直连环境）。
> 状态：**已实施**（2026-10-13，分支 feature/source-selection）——grill 三轮拍板后交付，终版范围较调研原案有四处变更，见文末「六、grill 拍板记录」。
> 缘起问题：① 多源台默认用哪个源怎么决定？② 能否手动指定源？③ 源之间有没有音质/延迟等差异？

---

## 一、现状机制（代码走读结论）

默认源决策 = **srcmem 记忆优先，否则 radio.txt 行序**，两级：

1. **静态序** = `s.u` 数组序 = radio.txt 同名行书写序。首行是台主 URL——收藏/最近/srcmem/健康标记的身份键。个人追加源（⚙ 面板 cfg.srcs）**只挂台尾**（封顶 6 条），不动顺序（`app.js:147-150`）。
2. **动态调整** = srcmem 成功源记忆：点播时若 `radio.srcmem` 记着该台上次试通源序号，提到最前（`player.js:114-116`）；建流成功后 `onAir()` 把赢的序号写回（FIFO 300 台封顶，`player.js:227-236`）。
3. 每源再展开最多 3 个 variant 级联：蜻蜓 m3u8 自动换算同 id 64k mp3 → 原始 URL → /proxy 兜底（`player.js:101-108`）；error/stalled(12s 看门狗)/ended 三路自愈顺延。
4. 手动选源：**现状没有**。⚙「备选源管理」（`app.js:651-665`）只有看全部源（行内带序号）/探活追加/移除追加，无「用此源播放/设为首选」。

即实际体验：首次点播按第一行源试（失败顺延），之后每次点播直接命中上次成功的源。

### xmcdn 实测（推翻「假流全假」预设）

抽测 5 台（live/55、521、963、964、708）：

- **manifest 是合法 HLS**（459 字节 `application/vnd.apple.mpegurl`，含正常分片表），但 **manifest 全都无 ACAO 头** → 浏览器 hls.js 直连必挂在 manifest 层，只能走 /proxy 绕行；分片本体（broadcast.tx.xmcdn.com）反而带 `ACAO:*`。
- **分片并非全假**：live/55、521、964 分片为 57KB 真 AAC（可用）；963、708 manifest 拉空（已死/漂移）。
- 结论修正：xmcdn 的真实画像 = **「manifest 锁 CORS（直连必挂、仅代理可播）+ 分片时好时坏」**，不是一律假流。AGENTS.md「已知坑」的假流表述建议按此更新；「探活必须验持续吐数据、不能信状态码/Content-Type」的结论不变，反被 963/708 再证一次。

### 运行时码率信息

全链路（player/app/server/update-sources）**无任何地方读 `icy-br`/`ice-audio-info` 响应头**；`/api/nowplaying` 旁路连接已建好但只读 `icy-metaint`（`server.js:98`）。UI 无处展示音质。蜻蜓换算硬编码 64k（`player.js:104`）。

## 三、源间真实差异（结论）

- **曲讯（ICY）——用户可感知差异最大**：仅直流 mp3/AAC 有；HLS 结构性没有（央广系全 m3u8 → 无歌名）。选哪个源直接决定有没有曲讯。
- **延迟**：结构性差异。HLS 天然多一个分片缓冲（直播常见 15~30s 级）；mp3/AAC 直流低得多；/proxy 仅加本地一跳可忽略。
- **可用性/CORS**：央广 ngcdn 锁 CORS 只能走 /proxy 第三级；xmcdn 见上节；蜻蜓建流 5–10s 属正常。
- **码率/音质**：数据层面不可判（可见码率差异 0 台），且链路上无任何读取/展示。**「按音质选源」当前既无依据也无入口。**
- 综合：同码率下「直流形态」是严格更优默认——不经代理（少一跳、不吃本地服务器带宽）+ 低延迟 + 有曲讯。

## 四、推荐方案：分层决策链 + 三件落地

### 默认源决策链（优先级从高到低）

```
① srcmem 记忆（已有）—— 上次试通源最前，绝大多数点播走这层
② 手动指定（新增）—— 当次点播最高优先，试通后 srcmem 自动承接
③ 静态启发式（新增，替代「上游行序」作无记忆时的默认序）
④ 级联自愈（已有）—— 任何失败顺延，srcmem 跟随现实自动校正
```

③ 只有一条判据、零网络成本：**首选「首个 variant 是直流形态」的源**（mp3/aac URL，或蜻蜓 m3u8——variants() 自动换算 64k mp3），m3u8 源次之，同级稳定排序保持上游行序。

### 落地清单

| # | 事项 | 位置/成本 | 效果与验收 |
|---|---|---|---|
| ① | play() 源排序启发式（score 纯函数 + 稳定排序，srcmem 提前逻辑不动） | player.js，~10 行 | 102 台「xmcdn 首源+蜻蜓次源」首次点播直接命中蜻蜓 mp3 直流，跳过「xmcdn 直连必败（manifest 无 ACAO）→ 代理绕行」整轮，且立刻获得曲讯。验收：清 localStorage 点播 Love Radio 103.7，应直接从蜻蜓源起播 |
| ② | 手动选源：`Player.play(s, prefer)` 序号参数；⚙ srcRowHtml 每行加「▶ 用此源播放」，正在用源高亮 | player.js + app.js，~25 行 | 人工调整入口；试通后 onAir() 写 srcmem，下次自动优先——手动与自动收敛同一机制，**不新增持久存储**。挂点现成（行内已带序号） |
| ③（可选） | icy-br 码率透传：`/api/nowplaying` 读头随曲讯返回，UI 展示「128kbps」 | server.js + app.js，~15 行 | 手动选源的质量依据；单独做价值薄，**建议并入 r2-B5 电台详情面板**（已进未来计划，本就规划「逐源体检状态」）同窗做 |

①+② 合计约 35 行，只碰 player.js/app.js，无新存储、无身份键变动、无新接口，模块契约无违反。

### 明确不做（及原因）

- **同步期重排/删 radio.txt 行**：行序即 `s.u[0]` 身份键，动了它存量用户的收藏/最近/健康标记/srcmem 全部失绑（身份公理）。radio.txt 保持上游行序，排序只在 play() 内存做——这也是启发式优于「同步期探活定序」的根本原因（后者还要逐台探测，同步时长从 1 分钟涨到分钟级）。
- **cfg.srcPref 持久首选存储**：与 srcmem 职责重叠，且断流顺延后两个记忆打架（手动选的源中途死、自愈切到源 2，持久首选还指着源 1，语义说不清）。手动选 = 「现在用这个源」一次性意图 + srcmem 承接，已够。
- **首播前并行探活选源**：首播加 4.5s+ 探活延迟不可接受，file:// 不可用，静态启发式已覆盖 103/120 台。

### 边界与残余风险

- 单源台（含 114 个仅 xmcdn 单源台）：排序无影响，行为不变；央广系 m3u8-only 台同分稳定序，不变。
- 启发式唯一误伤：直流源死、m3u8 活——首次点播先耗直流一轮（快败几秒，黑洞最坏 12s 看门狗），级联兜底 + 一次成功后 srcmem 永久校正，手动选源是最后人工兜底。相比现状（102 台首次点播必走一轮 xmcdn 无效直连+代理）整体严格更好。
- 多标签防双播/世代令牌走 play() 现有路径，自动兼容。

## 六、grill 拍板记录（2026-10-13，三轮，实施依据）

终版决策链（单次点播内从高到低）：**手动指定 prefer > srcmem 记忆 > 静态启发式 > 级联自愈**。与调研原案的差异：

| # | 差异点 | 拍板 | 原案 |
|---|---|---|---|
| 1 | **入口位置**：手动选源主入口放 footer（muteBtn 旁「源」按钮+浮层，正在听的多源台一键切源），⚙ 备选源管理保留 ▶ 作双入口（未播态预选源） | owner 提出（⚙ 四步深救不了急） | 只挂 ⚙ 面板 |
| 2 | **恢复默认源**（新增）：footer 浮层底部「↺ 恢复默认源」= 清该台 srcmem + 立即按启发式默认重播 | owner 提出（手动可控记忆，又不引入持久首选） | 无此项 |
| 3 | **存量 srcmem 一次性版本失效**：键升级 `radio.srcmem` → `radio.srcmem2`，旧记忆整体作废（否则已记 xmcdn 的台继续走代理旧路，① 对存量用户零收益） | grill 暴露的缺口，owner 拍板失效 | 无此项 |
| 4 | **③ icy-br 本期一并做**：server.js 随曲讯返回 br，footer 曲名行显示「· Nkbps」（仅 ICY 直流有） | owner 改判（原建议推迟 r2-B5） | 推迟 |

其余拍板：优先级语义（手动当次最高，试通后 srcmem 承接）；切源行为（一律立即切换并起播，暂停态同，点当前源=重连）；「正在用」高亮跟随 curSi（打开时取值，级联中不自动跳变）；「默认」徽标（启发式首选源，面板与浮层共用，恢复默认可预期）；单源台隐藏源按钮（按次渲染动态判定，同步后变多源自动出现）。

范围相应从「①+② 约 35 行只碰 player/app」扩为 **约百行、碰 player.js/app.js/index.html/server.js 四文件**；「明确不做」三条（不动 radio.txt 行序 / 不做 cfg.srcPref / 不做首播前并行探活）全部维持。
