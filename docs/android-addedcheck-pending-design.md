# Android addedCheck 持久待处理协议（设计草案，未接线）

基线：`5a7d643`。本文不是已实现的修复；不禁用全局同步，也不建议采用分离队列加盲重放。

## 问题与安全目标

轻更新和端内同步发布新 `radio.txt` 后才向 AppVm 返回 addedCheck，进程退出、协程取消、体检让位或 busy 时直接返回都会丢任务。下次 diff 已以新列表为旧侧，无法恢复。更早计算名单但在发布后落队列仍有同样窗口。Health.onDead 非幂等，简单重放可增加连续死亡次数，甚至误升停运档；健康写成功但队列确认前崩溃也不能盲重放。

目标：发布成功的每个已纳入 addedCheck 的项目至少保留到明确完成；写失败不得假确认；健康更新及完成见证原子提交；并发不覆盖导入或其他健康写。这里不承诺现有每批 500 截断之外的新增台，也不改变原有台名匹配语义。

## 建议协议（待实现和评审）

1. 发布前，先将带唯一批次 ID、原始名单和目标 radio 内容哈希的 prepare 记录原子持久化；必须合并此前未完成批次，不得以 500 截断历史积压。持久化失败则只拒绝本次发布，不全局禁用其他同步。端内同步需把 diff 计算移到写 radio 前。记录支持独立批次，不按台名全局去重，以免旧批次确认抹去新任务。
2. 发布必须串行；每次新发布前先持久解析前驱 prepare 的提交状态。仅已证明 committed 的批次可执行，不能按当前列表匹配推断发布成功。目标哈希不匹配时可能根本未发布，不能执行；无法证明状态则保留并停止该发布通道、明示恢复。旧/新哈希相同及 A→B→A 的 ABA 不能靠内容哈希判定：必须拒绝此类不明确提交，或引入可证明随发布原子推进且不会回退的世代见证；具体机制尚未实现。发布后的排队不得依赖调用方收到结果。
3. 体检先取主线程不可变的候选、身份和健康版本快照，再在 IO 探测。手动优先、网络失败、取消、被让位、未匹配、隐藏/全禁等均不确认对应任务；下次 Wi-Fi 启动及合适的空闲时机重试。必要时通过有界退避避免忙循环。
4. 使用 Store 单次原子写同时提交健康变更和私有完成见证（批次 ID + 项目 ID），而不是先写健康后删队列。该私有见证必须单独于 radio.* 白名单和导出数据，并且在 Store 初始化时加载、所有持久化路径保留；使用明确版本校验以及 copy-on-write，失败不改内存，版本冲突重新基于新快照决策，不能套旧结果覆盖健康写。考虑备份导入和回滚的版本检查，以及 rebind、健康清理、所有普通健康写与待检提交之间的串行化；探测期间身份/配置发生变化时保守丢弃结果，不确认任务。不能仅用 Store 的全局版本当作内存 Library 的完整并发证明。
5. 完成见证已落盘后才可异步整理 prepare 队列；即使整理失败或进程中断，重启时先读见证过滤已完成项，避免再次调用非幂等 onDead。队列整理和见证回收须有可证明的顺序及故障恢复，不能先删除见证；无法证明历史队列不可回退时不回收见证，容量满时拒绝新提交并明示，不能截断。导入不能抹去私有见证；回滚也不能无条件恢复旧见证。队列损坏/无法读取时 fail closed 并明示，不能当空队列覆盖。

## 需验证的关键边界

- 注入每个持久化步骤前后崩溃：prepare 前/后、radio 替换前/后、健康与见证事务前/后、队列整理前/后，重启核对无丢失且死亡次数最多增长一次。
- A→B→C 连续发布每步崩溃恢复、A→B→A 与旧新哈希相等、队列与 receipt GC 每步崩溃及旧快照回退；两次同步同名项目、不同批次，旧任务完成不得清掉新任务；同步发布失败留下的未发布 prepare 不得执行，也不得遗失旧任务。
- 手动体检抢占、boot 体检并发、取消、全网络失败、部分网络失败、库重载/配置变动、备份导入和回滚交错；写失败及版本冲突不确认。
- 文件损坏、存储满、队列积压、空名单、无匹配及隐藏/禁用台，均需定义可观察状态和有界资源策略。批次 ID 重复与见证清理顺序需要故障测试。
- 当前 `writeTextAtomic` 的 rename 原子性不等于断电持久化；若要求应对电源丢失，需另行验证文件和目录同步语义。上述主要针对进程崩溃/取消。

## 尚未解决

当前设计未定义跨多个版本列表完全失配时的终止/人工处理机制，也未完成 Store 私有见证与备份恢复事务的代码整合和并发证明。故本草案不能视为实现，也不应以盲重试代替上述工作。

未接线事务组件有两项**接线前阻断**：
- 导入旧健康快照时 receipt 仍保留，因此 ALREADY_APPLIED 只证明该操作曾经提交，绝不证明当前健康值仍包含其结果。需要设计导入世代、任务与见证的协调及回滚协议，定义导入后的恢复语义，完成交错测试前不得接线。
- 当前 Store 初始化区分不了瞬时读取失败与文件损坏；一旦读取失败会在后续普通持久化时写入永久 invalid 哨兵。私有事务随之 fail-closed，但重试、恢复、可观测性和数据修复机制均未设计；接线前必须解决，不能把瞬时故障当永久损坏。曾试验阻止所有持久化以保留原文件，但普通 set/remove 无返回值且 UI 仍报告成功，重启会静默丢失改动；该实验已撤回，不能以全库静默只读替代恢复设计。

导入语义必须先决定：历史 receipt 证明提交曾发生，并不保证该结果仍存在于导入后的健康快照；不能仅因导入改变世代就盲重放非幂等结果，也不能删除 receipt 假装未提交。需定义导入与待处理任务的界限、用户可见的未知状态及重新探测策略，并在完整导入/回滚和 Library 刷新协调域内证明一次性语义。

发布恢复候选方案：同一发布协调域先持久化含批次 ID、旧世代/哈希、新哈希及待检项的 prepare；下一次发布前必须解析前驱，未能证明发布的批次不得执行。若采用多文件 manifest，需在替换前验证旧资产和回退快照、最后提交 manifest；重启时逐项比对见证和资产，混态只能在回退快照完整可验证时恢复，否则保留证据并明确阻断该次发布，不能仅根据 prepare 阶段清理或假定未发布。此方案尚未实现，也不证明跨进程或硬件断电安全。

## 实验 codec（未接线、协议尚未冻结）

`GenerationManifestCodec` 仅是内存中二进制编码/严格解码实验，不读写文件或 current、资产、Store，也不改变同步行为。格式为大端 magic `VGMF`、版本 1、长度前缀 UTF-8 字符串与有序批次/任务数组；ID 采用规范小写 UUID 形状，哈希为 64 位小写十六进制。批次 ID 在清单内唯一，任务 ID 在批次内唯一，跨批次可复用；名单顺序和同名项目均保留。不为积压设 500 上限或推导任何容量策略。解码拒绝未知版本、无效 UTF-8、重复 ID、畸形长度、截断及尾随数据。格式和 ID 约束均属实验，不能作为已冻结持久协议。

**接线阻断：没有总字节数、字符串长度或条目数的资源预算。** 目前只检查声明长度不超过剩余输入，不能防止足够大的输入在编码、读取或解码时造成内存耗尽/OOM；调用者不得把它当作可安全读取不可信或任意大小持久数据的解析器。容量、输入限额与超限恢复策略尚未决定，本实验不以 500 或其他臆定数值冻结策略。

名字当前只要求非空且可严格编码为 UTF-8，允许 NUL、换行等控制字符，并非已清洗或适合日志、显示、行协议的数据；是否禁止、转义或保留控制字符及兼容规则尚待确定，接线前须明确并测试。

校验仅证明记录符合格式，不证明 ID 全局不可复用、哈希与真实资产相符、世代曾发布、任务可消费或发布安全；相同哈希的不同 ID 在模型中仍为不同世代，ABA 的提交判定仍需外部见证。资源预算、发布与恢复、接线及以下各项阻断仍待另行设计和验证。

## 另一候选：不可变世代 + 单 current 指针（未实现）

本节仅提出供评审的另一种发布线性化候选，不替换上面的建议协议或改变其接线前阻断结论，也不声称已解决问题。它要求所有参与者迁移后才可成立；只适用于已明确的单进程协调域，跨进程访问需另行设计。以下是候选约束，而非现有实现保证。

### 发布、读取与迁移

- 每个世代使用不可复用的唯一 ID，包含不可变 radio 资产、完整性元数据及该次新增任务批次；内容哈希只验完整性，不能充当世代身份或提交见证。将新世代在独立位置完整写入并验证后，原子替换唯一 `current` 指针；**指针替换是候选的发布线性化点**。成功返回前后崩溃均以重启后可验证的 `current` 为准，不凭调用返回值或内容相等猜测。`current` 不可读、所指世代缺失或校验失败时保留证据、停止发布和消费并明示恢复，不回退到看似可用的旧世代后继续写入。
- 读取一次 `current` 并固定该 ID，再从该世代读取整套资产；禁止一次操作中重复解析指针而混读不同世代。所有既有 reader、diff、启动加载、库重载、备份及其他读取固定 `radio.txt` 路径的调用点均须盘点并迁至同一解析入口；旧固定路径不能继续作为独立权威副本或从它推断提交。迁移需定义旧安装首次导入、升级中断重启、旧版本回退及无法迁移时的阻断；不得在仍有旧 reader 时宣称原子可见。读者持有世代期间须有 pin 或等价保护，释放后方可回收；启动后遗留 pin 的恢复和跨进程读者仍待设计。
- 发布串行：在协调域内基于已验证的当前世代计算 diff，构建新世代并将此前所有尚未完成的批次连同原有稳定 `(batchId, itemId)` 身份保留；不按台名全局去重、不用本批 500 上限截断积压。可以引用受保护的不可变任务清单，但其可达性和完整性必须同样验证。未切换指针的暂存世代不是已发布任务，不得消费；清理前先确认没有读者或恢复路径引用。
- 提交后消费从已提交世代及其保留的历史任务集合出发，与可信 Store 中 receipt 对账；完成旧项目不删除同名新批次。发布与任务确认交错时，候选实现必须在同一协调规则下重读或验证版本，保证继承的是完整积压；不能用过期快照覆盖新增任务或把未证明的完成当成完成。体检身份失配等仍依原草案保留和重试，不因换代自动确认。

### receipt、导入、GC 与 Store 信任

- 健康更新与对应 receipt 仍须在可信 Store 的一次可验证原子事务中提交；receipt 使用稳定任务身份，独立于可导入导出的用户数据，所有普通写入路径必须保留。导入旧健康值后，历史 receipt 仅证明曾提交，不证明导入后的值包含该结果；不得删除 receipt 或盲重放。导入、回滚、任务消费及 Library 刷新须共同协调，明确导入边界及未知状态；是否重新探测、如何形成新操作身份和告知用户仍待决定。导入失败或回滚也不得恢复过期 receipt 集合覆盖已提交的新见证。
- 世代 GC 仅在证明它既非 current、也不被任何 reader、恢复路径或仍需继承的任务引用后进行。receipt GC 更严格：只有已持久发布的压缩/检查点证明所有允许恢复的世代和队列都不再包含该任务，且旧快照、导入、回滚及在途 reader 无法重新引入它，才可在协调域内回收；证明不可得则保留 receipt，容量耗尽时拒绝相关新提交并提示，不截断。压缩发布、指针切换、世代删除、receipt 删除每一步崩溃后都需可恢复；不能先删 receipt 再希望旧任务不出现。
- 此协议依赖 Store 能区分可信已加载状态、瞬时读取失败和损坏，并提供可观察的失败、版本检查及失败不改变内存的事务；当前能力尚不满足接线前证明。未知或不可信时不得消费、确认、GC 或用空状态覆盖证据；普通写入的失败也必须对调用方可见，不能以静默全库只读冒充安全。恢复、修复和重试机制仍须单独设计。

### 协调顺序、验证与局限

候选锁顺序为发布/世代协调锁 → Store 事务锁；涉及 Library 的提交还须在一致的 Library 协调域内验证身份与版本，并先定义其相对锁序、线程切换和不持锁等待 IO 的规则。任何路径不得反向获取锁；网络探测在锁外执行，提交前重新验证。导入、回滚、普通健康写、GC 和发布都须列入锁序审计，避免死锁、旧快照覆盖与检查后变更。具体锁实现、跨进程锁及重入行为均待证明。

验收前应对世代写入、校验、指针替换前后、Store 健康+receipt 提交前后、导入/回滚、压缩与每次 GC 删除逐点注入进程崩溃和写失败；重启核对只有完整的旧或新提交世代可见、已发布任务不丢、未发布任务不执行、同一操作死亡次数至多增加一次。覆盖 A→B→C、A→B→A、相同内容不同 ID、旧 reader 与 GC、并发发布/消费/导入/普通健康写、损坏及存储满、重复 ID、锁顺序和死锁测试。单元故障注入不能代替真实文件系统上的验证。

原子 rename 及进程崩溃测试不证明掉电持久性或目录项顺序；若要承诺掉电安全，必须针对实际 Android 文件系统与 API 验证文件数据及父目录同步、指针替换和存储设备的持久化语义，不能假定已具备。开放问题还包括世代及任务空间上限、pin 恢复和旧版本回退策略、导入后的用户可见处置、Store 信任恢复、跨进程模型与平台持久化能力；这些未决项完成评审和测试前不得接线或宣称目标达成。
