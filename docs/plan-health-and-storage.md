## 一、背景与根因

### 1.1 死台定期全量复活(owner 报告)

症状:每次体检/同步后过一段时间,无效源电台全量回归,僵尸台数量爆炸。三重根因:

1. **主因——TTL 7 天自动过期**(`app.js:53`):死标记 `radio.health` 的 `t` 只在体检标死时写入,同步(`rebind` 保留原 t)与开机静默体检(仅收藏+最近 ≤30 台)都不刷新;全量体检是小时级操作,不可能 7 天一跑 → 必然全量复活,且过期后 boot 流程 `rebind→saveHealth` 把空标记写回,休眠快照一并抹掉,「✗ 无效源」按钮也随之隐藏。
2. **次因——FIFO 500 封顶**(`app.js:57-59`):与「全量体检标死几百台」同数量级,超限当场挤掉最旧标记,锯齿式部分复活。
3. **三因——同步重建后回绑失联**:欧美台整体重建(top-500 动态榜)、国内台 classifyCn 规则随 PR 调整,keyOf(分类|台名)与 URL 快照双通道都失联时标记休眠失效。

已排除:维护面板重置/配置导入(只动 radio.cfg)、git pull(不清 localStorage)、file:// 体检(P3-12 已修)。

### 1.2 localStorage 存储层评估

- **容量是伪危机**:8 个持久化键全部有界,现状 < 300KB;方案一落地后上限 ~1.5MB,占 5MB 配额三成。唯一只增不减的停运档天然封顶于 radio.txt 在列台数。
- **真痛点 = origin 绑定**:换浏览器/清浏览数据/换机器全丢;现有三个手动导出(收藏 m3u/配置 json/歌史 txt)分散、health 无导出、无一键完整备份。
- **否决项**:OPFS(数据仍在浏览器私有目录,换浏览器照样丢)、File System Access API(`showSaveFilePicker` Safari 不支持)、IndexedDB(仅放大容量,origin 绑定无解)。

## 二、方案一:死台分档修复(owner 已拍板主体参数)

### 2.1 两档模型

| 档位 | 判据 | 语义 |
|---|---|---|
| **疑似档**(短暂不可达:被墙/网络/运维) | 首次标死即入 | 默认隐藏;静默复测可达即撤销标记回归;复测仍死刷新 t 并累计 n |
| **停运档**(电台下线,如 HITFM 88.7) | 复测连续确认 ≥3 次 **且** 首死至今 ≥30 天 → 升级 | 永不因 TTL 复活;FIFO 最后才挤;保留「复测可达即撤销」保险通道(真停运永不触发,误判的唯一自动出口) |
| **休眠孤儿**(回绑失联的标记) | 同步后台没了/改名换 URL 对不上 | 90 天清理 |

补充参数:疑似档兜底 TTL **180 天**(纯数据卫生,正常使用碰不到;R1 挑战后维持——静默复测常态化下唯一触发场景 = 连续半年没开页面,复活反而是合理探测);FIFO 分额度 **疑似 1000 + 停运 1000**(合计约 1MB)。

技术事实(设计依据):单次探活无法区分「停运」与「被墙」——`/api/check` 只回答「此刻可达与否」,分档信号只能来自持续复测(时长+次数),故与静默复测机制配套。

### 2.2 机制改动

1. **静默复测**:`silentHealth` 范围从「收藏+最近 ≤30」扩为「收藏+最近 ∪ 死标记台」,每次 boot 一并跑(R1 拍板);活则撤销(自动回归列表)、仍死则刷新 t/累计 n(续期+为升级攒证据),停运档同样参与复测(保险通道)。**量级节流护栏**(R4 修订,语义全保留):每次只复测 t 距今 >24h 的标记、每 boot 封顶 200 条按最旧优先轮转(标记多于 200 时轮转全覆盖);停运档降频到 7 天复测一次——把 FIFO 顶格 2000 时的最坏 1-2 小时/次压回分钟级,同时终止对已停运台的永久日级探测。
2. **同步后增量体检**:口径 = 本次同步 diff **新增的国内台**(欧美台同步期已实测,跳过);**非**「无标记台」(防 localStorage 清空/换浏览器后退化为全量体检)。自动静默跑,复用体检通道与并发限流;与手动体检 busy 互斥沿用。
   - 依赖:server 同步 diff 需补 added 台的 URL 名单(现在只传数字 r.added 与 removed 名单)。
   - 「出现即健康」:不新增健康标记位——✓(ok)标记本就不持久化,visible() 只看 dead,无标记即显示,即现行语义。
3. **toast 两态**(新增极简组件,无障碍对齐 aria-live,不抢焦点):开始「后台体检新增 N 台…」/ 完成「N 台体检完成,X 台无效已隐藏」。
4. **数据结构兼容**:healthMarks 条目加首死时间 t0 + 连续确认次数 n 字段;旧数据按「疑似档、n=1、t0=旧 t」兼容读取,不做破坏性键升级。
5. **分档 UI 轻量区分**(R1 拍板):停运档行加「已停运」灰徽标,疑似档维持 ✗ 现状;title 文案分「疑似不可达(点击仍可尝试播放)」/「长期确认停运」。默认隐藏时两档均不可见,仅影响「✗ 无效源」翻开的排查场景。
5. **手动体检完成态分档统计**(R2 拍板):结束文案改「体检完成:可用 X、疑似失效 Y、已停运 Z」(Z 含本次新升级),与分档模型对齐。
6. **增量体检不设量级上限**(实施定案):diff 新增几十/几百台均照跑(并发 2 + toast 进度),数据新鲜度价值大于后台时间成本。
7. **首启基线(存量老台清库)**(R3+R4 拍板):升级后首次 boot 检测「基线未建」标志 → **toast 询问式引导(含预计时长),用户确认后开跑**全量体检(并发 2 静默版)——确认门槛防工作时间意外占带宽(owner 定:本人计划今晚下班/睡前确认开跑);范围**排除欧美两分类**(同步期已有实测证据,只清无证据的国内台)。**中断续跑**:跑过的台记临时进度,中断(关页/合盖)后下次 boot 跳过已确认的只测剩余(探活幂等);完成置位基线标志。手动体检优先让位(沿用 busy 互斥);file:// 下不跑不置位。存量大量从未标死的国内台靠此通道一次清干净。

### 2.3 边界与自洽性(审核自查)

- 停运档台复测复活 → delete 标记(再死从疑似档重来,n 归 1),不封死。
- 升级判据的 30 天跨度防短窗口网络抖动误升级;被墙类假死持续超阈值会误升级——启发式固有代价,出口 = 复测撤销 + 「✗ 无效源」开关手动翻出。
- 误埋(实际活的台被标死)不影响播放:行仍可点(title 有提示),任何体检/复测可达即自动回归。

## 三、方案二:存储层文件化(R1 拍板立项:方案 B 全套)

**路线:后端文件为主源 + localStorage 双写镜像 + 完整备份导出兜底**

- **键范围 = 全部 radio.***(R2 拍板,含 vol/view/showdead/theme 偏好标量):一套 Store 逻辑统一收敛,「完整备份」名副其实,偏好跟人走。
- **一致性消解 = 服务端唯一发号**(R2 拍板 rev 高者胜,R4 修订):rev 由服务端唯一发号(POST 成功才分配,客户端永不自造);localStorage 镜像存 lastServerRev + dirty 标记,后端写失败标 dirty,boot 时先重推 pending 再对账。冲突面归零;跨客户端并发退化为显式 last-write-wins(原 rev 方案在跨 origin 窗口会同 rev 不同数据、静默压掉一端改动——外部 review P0-2 证实)。
- **多标签同步本期做**(R2 拍板):BroadcastChannel 扩 'store' 消息(与既有 'on' 播放互斥消息同通道),他页收到后重拉后端刷新内存(~20 行);**debounce × 重拉竞争三规则**(R4 补,外部 review P0-5):序列化时点在 flush 执行时读当前内存(非 debounce 触发时)、收到他页消息先作废本地 pending 再重拉、beforeunload/visibilitychange→hidden 同步 flush pending。
- `server.js` 新增 `/api/store`(GET/POST `data/store.json`):复用 my-radio.txt 的 tmp+rename 原子写+串行队列基建;Origin 拒跨源、结构白名单校验(只收已知键已知形状)、2MB 封顶;`data/` 进 gitignore。
- 前端 Store 收敛层:写双写(后端主源,localStorage 永远留镜像);**boot 镜像先行渲染 + 后端异步对账**(R4 修订,防阻塞首屏):首屏用镜像立即渲染,后端读返回后对账——镜像 dirty 则重推 pending,后端新则应用并 re-render;file:// 降级模式原样走 localStorage。
- **静态隔离**(R4 补,外部 review P0-1):静态服务过滤器加 `data` 段拒绝(与 dotfile/.bak 同口径一行)——否则 GET /data/store.json 直接暴露全量个人数据(HOST=0.0.0.0 局域网模式下是实际风险)。
- ⚙ 面板加「完整备份导出/导入」(全部 radio.* 打包单 JSON,导入全量覆盖 + confirm,口径同配置导入);现有三个单项导出保留(面向外部用途)。
- 写放大对策:`radio.volperst` 拖动连续写 → Store 层 ~300ms debounce(health 体检收尾本就攒批)。

工作量:server ~60-80 行 + 前端 Store ~100-150 行。
