# 0003 不做客户端时移（暂停续播仅限已缓冲窗口）

直播电台「暂停后继续接着听旧内容」的需求（2026-10-15 提出）评估后拍板：不做客户端时移/录流。暂停续播维持现状——只能接上客户端**已缓冲**的那部分，缓冲耗尽由既有断流自愈兜底重连落直播头；「主动回到直播头」另做手动刷新（docs/plan-refresh-live.md）补足控制权。

物理前提：直播服务器不保留过去——Icecast/Shoutcast 直流无 seek/Range，重连必落直播头；HLS 电台 playlist 滑动窗口普遍只留几个分片，旧分片滚出即不可得。所以「暂停续播旧流」的时长上限 = 恢复时客户端已缓冲的数据量（浏览器/Media3 内部策略决定，应用层对直流台无抓手），任何客户端技巧都无法找回已错过的音频。

## 考虑过的选项（否决理由留档，防日后再提）

- **录流 + MSE 影子缓存（直流台 fetch 抓流进 SourceBuffer，暂停期持续录）**：内存 ~1MB/分钟须设上限，超限后「继续」照样断（时移仍有限）；1600+ 台编码动物园长尾（mp3/AAC ADTS/畸形头逐个趟）；Safari 不支持 audio/mpeg MSE；/proxy 链路与蜻蜓慢建流全要重验证；等于重写播放引擎，与零依赖、极度紧凑的定位相悖。
- **调大 hls.js `maxBufferLength` 延长 HLS 台暂停窗口**：受服务端直播窗口封顶（电台 playlist 普遍只留几个分片），直流台（占多数）完全无抓手；收益封顶不值得多一条配置面。
- **维持现状 + 手动刷新（采纳）**：暂停续播=已缓冲窗口（零成本白送）；窗口外自动兜底回直播头（缓冲耗尽后唯一非死解，看门狗/级联既有机制）；手动刷新给「我要最新的」一个明确入口。

## 后果

「暂停后继续旧流」的时长由浏览器/Media3 缓冲策略决定，**不构成产品承诺**，两侧（Web/Android）均不为此写文档承诺。未来若要真时移，属引擎级重构，须重开 ADR 推翻本决策。评估依据见 docs/plan-refresh-live.md 第 1 节。
