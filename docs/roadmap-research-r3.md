# VRadio 后续扩展方向调研（GitHub 同类项目对标 r3）

> 调研日期：2026-11-14
> 调研方式：agent-reach 的 GitHub CLI 后端，结合本地仓库现状、`docs/roadmap-research-r2.md`、`docs/expansion-analysis.md`、`docs/android-iteration-research-2026-10-18.md` 与当前 Android/Web 代码复核。
> 目标：在现有能力已经比较完整的前提下，找出后续可以自然迭代的产品功能、实现方案、成本、难度和边界。
> 借鉴纪律：只借鉴功能和实现原理，不直接复制外部项目代码；引入第三方数据或服务前单独核对国内直连性、许可和隐私影响。

---

## 一、当前判断

VRadio 已经完成了普通网络电台播放器的大部分核心能力：

- 收藏、最近播放、搜索、分类、网格/列表视图；
- 多源决策、成功源记忆、断流自愈、手动刷新回直播头；
- ICY 曲讯、码率显示、歌曲历史；
- 台标三级来源和收藏优先补全；
- 维护面板、添加自定义电台、追加备选源；
- 死链体检、疑似/停运分档、开机静默复查；
- Web 与 Android 的共享数据格式和 `radio.*` 持久键契约；
- Android 原生播放、Media3、锁屏控制、媒体键、启动续播、快捷方式、M3U 导入、备份 v2 和数据更新。

因此，下一阶段不适合继续无差别增加台数或堆叠外部服务。更有价值的方向是：

1. 让用户知道某个源为什么失败，并能自己修复；
2. 让同步数据更干净、稳定和可追溯；
3. 让电台库更适合发现和迁移；
4. 补足 Android 形态天然适合的能力；
5. 继续保持本地优先、无账号、无遥测、零依赖和国内直连定位。

成本口径如下，默认开发者已经熟悉当前代码，成本包含基本测试和文档，不包含长期内容维护：

| 级别 | 估算 |
|---|---:|
| 小 | 0.5–1.5 人日 |
| 中 | 2–5 人日 |
| 大 | 6–12 人日 |
| 很大 | 2–6 周 |

难度使用 1–5 级，综合考虑架构风险、网络不确定性、数据迁移和 Web/Android 双端同步成本。

## 三、优先推荐的扩展

### 1. 电台详情与逐源诊断中心

这是当前最值得优先做的方向，也是现有路线图已经确认的 `r2-B5`。

目前用户能看到台是否失效、是否有多个源、是否正在播放，但无法知道某个源失败的具体原因。详情页应收拢以下信息：

```text
台名
分类 / 台标 / 收藏状态
当前播放源：源 2 / 4
源列表：
  ✓ 源 1  mp3   128kbps  直连  320ms
  ✗ 源 2  m3u8           代理  连接超时
  ? 源 3  AAC             未检测
歌曲历史
复制当前源地址
编辑 / 追加 / 删除 / 调整源顺序
```

实现落点：

- `app.js`：详情弹层、当前台状态、历史和维护入口；
- `player.js`：暴露当前变体序号、成功源和播放模式；
- `server.js`：扩展 `/api/check` 返回结构化探活信息；
- `sync.js`：复用已有探活执行器；
- Android：复用 `CheckStream`、`SrcSheet` 和 `PlayerHolder` 状态。

成本：Web 3–5 人日，Android 3–5 人日，双端合计 6–10 人日，难度 3/5。

产品收益是把“自动容错”升级成“用户可理解、可修复的容错”。

### 2. 备选源生命周期管理

当前已经支持追加备选源，但还可以补足完整管理能力：

- 手动调整源顺序；
- 暂时停用某源；
- 删除错误源；
- 替换源但保留电台身份；
- 显示源健康历史；
- 将成功源设为临时优先源；
- 一键恢复默认源列表；
- 区分直连源、HLS 源和代理源。

必须继续遵守现有身份公理：不能直接修改主 URL，否则会破坏收藏、最近播放、健康标记和成功源记忆。建议把源编辑继续放在 `radio.cfg`，让 `player.js` 的 `variants()` 统一计算最终顺序。

可以考虑扩展成：

```json
{
  "srcs": {
    "https://main-station-url": [
      "https://user-source-1",
      "https://user-source-2"
    ]
  },
  "srcDisabled": {
    "https://main-station-url": [
      "https://dead-source"
    ]
  },
  "srcOrder": {
    "https://main-station-url": [
      "https://user-source-2",
      "https://main-station-url",
      "https://user-source-1"
    ]
  }
}
```

成本：Web 3–5 人日，Android 极简编辑 4–6 人日，合计 7–11 人日，难度 3/5。

它直接解决“流地址漂移后用户只能等待同步”的实际问题。

### 3. 电台源质量中心

[Receiver](https://github.com/meehow/receiver) 的核心启发是：电台目录的价值主要来自可用、干净、少重复，而不是台数越多越好。

VRadio 当前健康模型主要回答“这台现在是不是死了”。下一步可以记录聚合质量指标：

- 最近成功探活时间；
- 最近失败时间；
- 连续失败次数；
- 平均连接耗时；
- 首次出声耗时；
- 播放过程中的断流次数；
- 有效流持续时间；
- 是否需要代理；
- 是否能读取 ICY 曲讯；
- 是否能读出码率；
- 源数量和直连源数量；
- 最近 30 天成功率。

用户界面不必做成复杂 dashboard，可以只显示：

```text
稳定性：良好 · 近 30 天 4 个源中 3 个可用
```

第一阶段只保存聚合值：

```json
{
  "lastOk": 1731500000000,
  "lastFail": 1731490000000,
  "okCount": 12,
  "failCount": 3,
  "lastLatency": 420
}
```

不建议把所有探活明细永久塞入 `radio.health`，否则会快速放大存储体积。可以只保留最近几次明细，长期数据使用聚合值。

成本：基础版 4–7 人日，完整质量历史 8–12 人日，难度 4/5。

### 4. 同步管线增加去重、来源追踪和替换前校验

当前同步已经具备双上游、欧美台逐个实测、分类重建、diff 摘要、原子写入和失败保留旧列表。下一步可以增强为轻量数据质量流水线：

```text
拉取上游
  ↓
格式解析
  ↓
名称清洗
  ↓
URL 归一化
  ↓
同名 / 同源去重
  ↓
探活抽样
  ↓
生成候选 radio.txt
  ↓
和旧版本对比
  ↓
达到质量阈值后原子替换
```

同步报告可以记录来源和质量，但不改变 `radio.txt` 契约：

```json
{
  "source": "gao",
  "upstream": "github mirror",
  "checkedAt": 1731500000000,
  "added": 32,
  "removed": 14,
  "deduped": 21,
  "invalid": 8,
  "euKept": 184
}
```

成本：4–8 人日，难度 4/5，另有持续内容维护成本。

它能让项目从“有很多台”逐步变成“打开后大部分都值得点”。

### 5. 第三上游：人工精选电台集合

这个方向已经在现有路线图中，建议继续推进，但要保持精选层边界：

- 只加入真正有特色的音乐台；
- 不继续增加大量固定分类；
- 仍归入现有“欧美音乐”；
- 同步阶段实测；
- 保留来源和许可信息；
- 不把外部列表全量照搬进主库。

[recommended-radio-streams](https://github.com/deroverda/recommended-radio-streams) 提供了人工筛选的独立音乐台、氛围台、爵士台和实验台，可以作为精选层来源。

推荐数据层：

```text
主库：国内公开电台 + 已验证欧美主流台
精选层：人工选择的高质量特色台
个人层：my-radio.txt
```

成本：接入代码 2–4 人日，首次清洗 2–4 人日，长期维护每周约 0.5–1 人日，难度 2/5，内容维护难度 4/5。

### 6. 策展式电台集合

[Aerial](https://github.com/shapeshed/aerial) 的“按心情和活动策展”值得借鉴，但不建议把它变成新的固定分类体系。

可以增加轻量集合：

```text
今日推荐
适合工作
适合夜间
华语怀旧
欧美经典
新闻与谈话
低码率省流
稳定直连
```

集合本质上是 URL 集合，而不是新的电台身份：

```json
{
  "collections": {
    "适合工作": ["https://..."],
    "夜间收听": ["https://..."]
  }
}
```

第一版可以由项目维护；第二版再允许用户创建自己的集合。

成本：内置集合 2–4 人日，用户自定义集合 4–7 人日，难度 2/5，内容维护成本中等。

它比继续增加省份、流派等列表维度更容易保持界面清晰。

### 7. 本地发现页

当前搜索、收藏和最近播放解决的是“找已知电台”。可以增加一个小型发现入口：

- 稳定直连；
- 最近新增；
- 最近恢复；
- 有曲讯；
- 低延迟；
- 欧美精选；
- 本地收藏最多；
- 最近没有听过。

不需要账号，也不需要云端推荐，可以基于已有本地数据计算：

```text
stable = health.okRate + directPlayable + lowFailureCount
fresh = sync.addedAt
unheard = station not in recents
metadata = station has nowplaying support
```

成本：基础发现页 2–4 人日，带质量分数 5–8 人日，难度 3/5。

第一版应只依赖本地健康状态、同步 diff 和精选名单，避免运行时依赖国外目录服务。

### 8. 跨格式导入：PLS、XSPF、ASX

Android 已经放宽了任意 M3U 导入，下一步可以补齐播放器生态常见格式。

[OmniBeat](https://github.com/Vikindor/omnibeat) 支持直接流 URL、PLS、M3U、HLS、XSPF、ASX、WAX、WMX、DASH 等格式；[PyRadio](https://github.com/coderholic/pyradio) 也强调 M3U 和多播放列表兼容。

建议按以下顺序实现：

1. PLS；
2. XSPF；
3. ASX/WAX/WMX；
4. 带相对 URL 的 M3U；
5. 带 `group-title`、`tvg-logo`、`tvg-id` 的 M3U。

解析结果统一成：

```js
{
  name: "台名",
  url: "https://...",
  category: "自定义",
  logo: "https://...",
  externalId: "..."
}
```

继续复用 `safeTarget`、URL scheme 校验、长度/数量封顶、名称清洗和导入确认。导入文件中的 URL 不应全部自动发起网络请求。

成本：Web 2–3 人日，Android 2–4 人日，双端合计 4–7 人日，难度 2/5。

### 9. 统一备份格式 v3

Android 已经有 backup v2，Web 也具备收藏、配置和歌曲历史的分别导出能力。后续应把备份格式变成正式的跨端数据协议。

建议 v3 明确包含：

```json
{
  "format": "vradio-backup",
  "version": 3,
  "createdAt": 1731500000000,
  "app": "web",
  "data": {
    "radio.favs": "...",
    "radio.recents": "...",
    "radio.cfg": "...",
    "radio.songs": "...",
    "radio.volperst": "..."
  },
  "myRadio": [
    "自建,#genre#",
    "我的电台,https://..."
  ],
  "collections": {},
  "notes": {}
}
```

必须包含：

- schema version；
- 来源端标记；
- 导入前预览；
- 导入后的冲突策略；
- 未知字段处理策略；
- 导入结果统计；
- 导入失败时不破坏已有数据。

成本：2–4 人日，难度 2/5。

### 10. 自动校验 Web/Android 持久键契约

目前新增任何 `radio.*` 键都需要手动修改：

- `store.js`；
- `server.js`；
- Android `Consts.kt`；
- 备份过滤逻辑；
- 测试。

建议新增根目录契约文件：

```json
{
  "keys": {
    "radio.favs": {
      "type": "json",
      "persist": true,
      "backup": true,
      "web": true,
      "android": true
    },
    "radio.logos": {
      "type": "json",
      "persist": false,
      "backup": false,
      "web": true,
      "android": true
    }
  }
}
```

第一阶段不需要代码生成，只需要零依赖测试：

```bash
node test/contracts.js
```

校验以下内容：

- 三侧白名单是否一致；
- 备份是否覆盖应该备份的键；
- 是否存在未声明的 `radio.*`；
- Web/Android 值域是否一致；
- 迁移是否有测试。

成本：2–4 人日，难度 2/5，长期价值很高。

### 11. Android 主屏小部件和快速操作

Android 是 VRadio 最适合增加原生能力的地方。

第一版只做：

- 当前电台名；
- 播放/暂停；
- 上一个收藏台；
- 下一个收藏台；
- 台标；
- 点击打开应用。

实现路线：

- 使用 `RemoteViews`，保持依赖白名单；
- 通过 `MediaController` 控制 `PlaybackService`；
- 小部件只订阅 `PlayerHolder.ui` 的少量状态；
- 不在小部件内实现完整列表；
- 收藏变化后刷新小部件；
- 播放状态变化时局部更新。

成本：3–5 人日，难度 3/5，国产 ROM 兼容性验证成本中等。

### 12. Android 定时播放和睡眠策略

Web 端已有睡眠定时，Android 可以提供原生定时播放：

- 定时停止；
- 指定时间开始播放某个收藏台；
- 工作日自动播放；
- 低电量时禁止自动启动；
- 仅 Wi-Fi 下执行源更新；
- 夜间自动降低通知干扰。

第一版建议只做单次定时：

```text
今天 23:30 停止
明天 07:30 播放「中国之声」
```

实现可以使用 `AlarmManager` 或 `WorkManager`，触发后启动 `PlaybackService`，同时处理通知权限、Doze、后台启动和音频焦点。

成本：3–6 人日，难度 3/5，风险主要来自国产 ROM 后台限制。

Web 端不重新引入闹钟。浏览器后台自动播放受限，形态不适合。

### 13. Android 网络策略和流量保护

当前 Android 已经对同步和体检做了 Wi-Fi、电量等限制，但播放策略可以更明确：

- 播放允许移动数据；
- 同步默认 Wi-Fi；
- 体检默认 Wi-Fi；
- HLS 代理提示可能产生更多流量；
- 移动数据下显示估算码率；
- 低电量时暂停后台同步；
- 断流重试次数受网络类型影响。

流量可以先使用：

```text
码率 × 播放时长 ÷ 8
```

做估算，不需要一开始精确统计每个字节。

成本：2–4 人日，难度 2/5。

### 14. Android Auto / 车载模式

[RadioDroid](https://github.com/segler-alex/RadioDroid) 说明 Android Auto 是成熟方向，但它不是低成本扩展。

需要处理：

- `MediaBrowserService`；
- 收藏、最近、分类树；
- 车载端安全交互限制；
- 播放错误和源切换反馈；
- 网络变化；
- Android Auto 模拟器和实体设备差异。

成本：第一版 7–12 人日，加实体设备验证可能达到 2–3 周，难度 4/5。

建议继续观察真实需求，不要因为同类项目支持就立即排期。

### 15. 本地局域网遥控

[PyRadio](https://github.com/coderholic/pyradio) 的远程控制和 [Radiotray-NG](https://github.com/ebruck/radiotray-ng) 的 DBus 接口提供了“播放器和控制界面分离”的参考方向。

VRadio 可以做成可选局域网能力：

```text
浏览器 A：播放
浏览器 B：遥控
手机：控制电脑上的播放器
```

最小接口可以是：

```text
GET  /api/player
POST /api/player/play
POST /api/player/pause
POST /api/player/next
POST /api/player/volume
```

必须默认关闭，并增加局域网监听限制、随机 token、Origin/Host 校验、只读状态和 URL 安全限制。

成本：7–12 人日，难度 4/5。

它有一定高级用户价值，但优先级低于逐源诊断和 Android 原生能力。

### 16. 回听与时移

真正的时移不是“暂停后继续播放”，而是持续建立一个本地环形缓冲：

```text
持续录制当前流
  ↓
本地环形缓冲
  ↓
按时间戳读取
  ↓
回退 15 秒 / 60 秒
  ↓
追赶直播头
```

VRadio 需要面对 MP3/AAC 直流、HLS、代理、多源切换、网络不稳定和不同台时间戳差异。建议 Android 先做 Spike：

- 只支持一个 MP3/AAC 直流；
- 只保留最近 60 秒；
- 暂不支持 HLS；
- 不写入永久文件；
- 不承诺所有台可用。

成本：Spike 3–5 人日；可用的 Android 单格式版本 10–20 人日；Web 通用版本更高；难度 5/5。

### 17. 录音和逐曲保存

[Radio Recorder](https://github.com/sfuhrm/radiorecorder) 展示了逐曲录音、ID3、并行录制和元数据 CSV，但这个方向和 VRadio 当前边界冲突较大：

- 需要存储音频；
- HLS 分片录制复杂；
- 版权风险明显提高；
- 手机存储和后台限制复杂；
- 逐曲切分依赖曲讯质量；
- Web 和 Android 难以保持一致；
- 需要重新审视当前免责声明。

成本：Android 基础录音 7–15 人日；逐曲、ID3、HLS、多台并行 2–4 周；难度 5/5。

建议继续观察，不作为近期产品计划。

### 18. 元数据管线 v2

[RadioPlayer](https://github.com/jailsonsb2/RadioPlayer) 展示了“曲名 → 专辑封面 → 歌词 → YouTube MV”的完整链路，但这很容易把电台播放器带向音乐识别产品。

VRadio 更适合先增强本地可控的元数据处理：

- 统一拆分 `Artist - Title`；
- 去除电台台名重复前缀；
- 区分节目名和歌曲名；
- 清理空曲讯；
- 相同歌曲去重；
- 记录元数据来源；
- 区分 ICY 直读和外部旁路；
- 统一歌曲历史中的台名、时间和码率。

歌词可以作为 Android 的可选能力，但应做到有结果才显示、不阻塞播放、服务不可达时静默降级。

成本：元数据清洗 2–4 人日；结构化管线 4–7 人日；歌词接入 2–4 人日；难度 2–4/5。

### 19. 最小化本地收听统计

建议保持“一行总结”形态，不做 dashboard，也不上传数据：

```text
最近 7 天收听 12 小时
最常听：中国之声
最常用分类：华语音乐
最常用时间：22:00–24:00
最稳定的台：Radio Paradise
```

可以按日保存聚合数据：

```json
{
  "2026-11-14": {
    "ms": 1820000,
    "stations": {
      "https://stream.example/a": 1200000
    }
  }
}
```

不要记录每秒状态、完整行为明细或远端用户画像。数据量必须受控，不能让 `radio.*` 变成无限增长日志。

成本：Web 2–4 人日；Android 3–5 人日；难度 2/5。

### 20. 发布和分发能力

Android 后续还需要降低安装和升级成本：

- GitHub Release 自动发布 APK；
- debug/release 包区分；
- SHA-256 校验；
- 变更日志；
- 手动检查更新；
- F-Droid 元数据；
- 国内可下载的 Release 镜像说明；
- Web 根目录打包下载；
- `radio.txt` 与 APK 版本解耦。

成本：自动发布和校验 2–4 人日；F-Droid 元数据和流程 2–5 人日；难度 2/5。

## 四、建议排期

### 第一阶段：可靠性增强

建议优先安排：

1. 电台详情与逐源诊断；
2. 备选源排序、停用、删除；
3. 探活结果结构化；
4. 同步去重和质量报告；
5. Web/Android 持久键契约自动校验。

这一阶段解决的是“某台为什么播不了、应该怎么修”的核心问题。

### 第二阶段：迁移和发现

建议安排：

1. PLS/XSPF/ASX 导入；
2. 统一备份格式 v3；
3. 策展式电台集合；
4. 精选第三上游；
5. 本地稳定台、最近新增台发现页。

这一阶段提高内容质量和换机迁移体验，同时不破坏现有产品边界。

### 第三阶段：Android 原生体验

建议安排：

1. 主屏小部件；
2. 快速操作；
3. 定时播放；
4. 流量和省电策略；
5. Android 极简维护菜单；
6. Android Auto 先做需求验证，再决定是否开发。

### 第四阶段：只做技术验证

只建议做 Spike 或小范围试验：

1. 直播时移；
2. 局域网遥控；
3. 录音；
4. 多设备控制；
5. 外部歌曲识别、歌词和 MV。

---

## 五、明确不建议跟进的方向

### 1. 运行时直接依赖 Radio Browser 全量目录

Radio Browser 适合发现和补充数据，但国内运行时可达性、接口稳定性、URL 质量和现有 URL 身份模型都存在冲突。更适合在同步阶段使用镜像或快照，生成可离线消费的数据。

### 2. 继续增加大量分类维度

省份、流派、语言、国家等维度全部铺开后，列表会越来越难用。应优先使用搜索、策展集合和发现页。

### 3. 专辑封面、歌词和 MV 全链路

这些能力在同类项目中很常见，但会引入外部 API、匹配错误、中文曲库弱、服务不稳定和隐私边界问题。建议先做元数据结构化，歌词只作为可选适配器。

### 4. PWA 深化和桌面托盘

Web 端当前定位是本地 HTTP 播放器，Android 已经是明确的原生移动路线。继续做 PWA 安装、桌面托盘或 Electron/Tauri，会增加分发和兼容成本，但不一定提升核心收听体验。

### 5. 云账号和云同步

这会改变单用户本地工具的定位，引入账号、服务器、认证、隐私和数据迁移问题。当前统一备份文件已经能够解决大部分换机需求。

### 6. 多房间、AirPlay 和 Chromecast

这些能力依赖设备发现、平台 SDK 或额外协议栈，和零依赖、国内直连的产品约束不匹配。

### 7. 录音优先于播放可靠性

录音需要存储、后台任务、HLS 处理、曲讯切分和版权边界。应该等源可靠性、Android 分发和用户需求都稳定后再重新评估。

## 七、推荐的实际开工顺序

如果只选择下一批最值得做的内容，建议顺序是：

1. `radio.contract.json` 和 `test/contracts.js`，先把 Web/Android 契约自动守住；
2. 电台详情面板；
3. 逐源探活结果和源管理；
4. 同步质量报告与去重；
5. PLS/XSPF 导入和统一备份 v3；
6. 精选第三上游和策展集合；
7. Android 小部件、定时播放和流量策略；
8. 最后再评估时移、局域网遥控和 Android Auto。

这个顺序的共同特点是：先解决当前用户最容易遇到的“播放失败和无法修复”，再提升发现与迁移，最后才进入需要长期维护或额外平台支持的大型能力。
